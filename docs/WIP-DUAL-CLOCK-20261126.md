# Незавершённая работа: dual PTP, 26 ноября 2026

Ветка `wip/dual-clock-peer-roles-20261126`, база `main` на момент остановки — `7ceb1b4`. Не сливать без завершения проверки. Изначальный вариант `feat/dual-clock-roles` объединял адреса источников и получателей, поэтому исходящий master мог слать Sync самому источнику. В этом черновике раздельные peer interests для входящих сессий и исходящих групп; пересечение по IP отклоняется, источники обновляются через `set_session_peers`, группы — через `set_group_peers`. Lease и прежний одноролевой режим сохранены. Опубликованы `shared_service` и dual mapping как экспериментальный API.

Локально `cargo test --offline -p timesync --lib` — 50/50, `cargo test --offline -p clock --lib` — 67/67, `cargo test --offline -p airplay --no-run` успешно. В полном `airplay --lib` один тест MRP упал, потому что он принимал unsolicited DeviceInfo за ответ на свой запрос. В ветку включена поправка теста; **после неё тесты повторно не запускались**. Реальные устройства и полный RX → relay → TX не проверялись.

Перед интеграцией: повторить все тесты после правки MRP, проверить атомарность и отмену обновлений разных owners, одновременное истечение peer leases, конфликт портов и совпадение источника/получателя, loss/restart входящего clock, цепочку PtpGroup и остановку исходящего релея при потере входного времени. Проверить, что `TimeSync::start_host_dual` и источник `MasterTimeline` композиционно используют один физический clock, что выбранный API пригоден для фронтенда, и что одноролевой режим не изменился. IPv6 и аппаратная синхронизация отдельно. Код в этом виде — рабочая гипотеза, а не завершённое решение.
