# Обратные команды с пульта

> Историческая заметка о реализации. Сведения о базе ветки и тестах ниже относятся к моменту написания; текущее состояние — в [STATUS](STATUS.md).

Ветка `feat/remote-control` от `origin/main` (`847fe38`). На дату заметки ветка ещё не была влита.

## Что проверено

- MRP `SEND_COMMAND_MESSAGE` маршрутизируется в `remote::Control`:
  play, pause, toggle, stop, next, previous и seek. Громкость
  (`SET_VOLUME_MESSAGE`) идёт в `Control::volume` через отдельную очередь,
  чтобы пачка значений ползунка не блокировала чтение MRP.
- Повтор MRP-запроса с тем же `ProtocolMessage.identifier` подтверждается
  успешно, но приложение повторно не вызывается. Память ограничена 64
  идентификаторами по 256 байт; без identifier поведение прежнее.
- Потеря канала событий отправителя отвязывает пульт (`Remote::detach`):
  команды больше не принимаются, а новое соединение не получает команды
  старой сессии. Очередь команд не переигрывается.
- Успешная отправка в очередь — это принятие, а не подтверждение
  исполнения отправителем.

## Протоколы

MRP (AirPlay 2, поток 130) и legacy DACP — разные пути, и это не
скрывается. В этом профиле используется MRP-подобный
`sendMediaRemoteCommand` по каналу событий; protobuf-номера MRP Command
(`1..6`, `45`) не совпадают с DACP-путями. DACP-ID/Active-Remote и
`_dacp._tcp` для AirPlay 2 не выдаются, поэтому DACP не подставляется
молча вместо MRP. Для AirPlay 1 обратный пульт остаётся отдельной
протокольной задачей (см. отчёт по AirPlay 1).

## Тесты

- `services/remote/src/tests.rs`: полный MRP-сеанс карточки, all command
  replies, повтор `identifier` не выполняет next дважды.
- `services/media/src/control.rs`: `Remote` без отправителя, чужой detach,
  потеря канала и отсутствие переигранных команд у нового владельца.
- `services/remote/src/mrp_service/control.rs`: маршрутизация команд,
  seek, громкость и изменение карточки только после принятия командой.

`cargo test -p remote -p media --offline`: 74 + 27 + вспомогательные
тестовые бинарники, все прошли.

## Ограничения

- **Аппаратной проверки не было**: реальных Apple TV/колонок и пультов
  в окружении нет. Проверены только каналы и маршрутизация в коде.
- DACP-сервер/клиент не реализован; это явно отдельный профиль.
- «Команда принята» в тестах означает запись в очередь приложения, а не
  подтверждение от физического отправителя.
