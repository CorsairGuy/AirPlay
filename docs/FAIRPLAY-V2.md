# FairPlay v2 (SAPv2.5): что нужно приёмнику

Сверено 25 ноября 2026. Статус: **не реализовано**, v2 отклоняется явной ошибкой.
Текущее состояние ядра — [STATUS](STATUS.md); источники — [REFERENCE-AUDIT-20261125](REFERENCE-AUDIT-20261125.md).

Документ отвечает на три вопроса: чем v2 отличается от v3 и от «mode 2 внутри v3»,
каких данных не хватает для реализации, и как их снять на Mac. Он не является
спецификацией Apple и не подтверждает совместимость с macOS.

## 1. Короткий вывод

- **Протокол v2 известен полностью**: framing, размеры сообщений, поля, порядок
  проверок подтверждены захватами (`OBS`) и референсной реализацией (`RE-CODE`).
- **Криптопримитив v2 публично существует только как производные константы**
  внутри LGPL-реализации, полученные трассировкой Apple CoreFP. Политика §0.5
  (только идеи/структура/wire-факты, код пишется с нуля) запрещает перенос такого
  материала. Без отдельного решения владельца проекта реализация v2 в ядре
  невозможна — это не техническое, а provenance-ограничение.
- **v2 сам по себе не даст музыку с Mac.** Наблюдения показывают, что macOS Music
  идёт по RAOP/AP1 (`ANNOUNCE`), а classic AP1 RX в ядре отсутствует
  (`ANNOUNCE` → 501, тест `session.rs`). Нужны оба слоя.
- **Публично нет ни одного полного вектора v2**: нет M2, ответа на M2 и `ekey`.
  Поэтому аппаратную проверку нельзя заменить чтением исходников.

## 2. Версия ≠ mode

Самая частая ошибка — принять `0x02` в теле M1 за «FairPlay v2». В M1 два разных
байта, и они означают разное:

| Клиент | M1 (16 байт) | byte[4] | byte[14] |
|---|---|---|---|
| iOS/iPadOS (AirPlay audio) | `46 50 4c 59 03 01 01 00 00 00 00 04 02 00 01 bb` | `03` | `01` |
| macOS, зеркалирование | `46 50 4c 59 03 01 01 00 00 00 00 04 02 00 00 bb` | `03` | `00` |
| macOS Music | `46 50 4c 59 02 01 01 00 00 00 00 04 02 00 02 bb` | **`02`** | `02` |

- `byte[4]` — версия профиля FairPlay (`03` — PlayFair/v3, `02` — v2/SAPv2.5).
- `byte[14]` — mode (селектор набора ключей), 0..3.
- `byte[12] = 0x02` — маркер payload, `byte[15] = 0xbb` — константа.

Отсюда: **v3 с mode 2** — это третий предвычисленный ответ из нашей таблицы
`REPLY_MESSAGE[2]`, а не v2. Признак v2 — только `byte[4] == 0x02`.

В v3 mode выбирает одну из четырёх готовых 142-байтных «заготовок». В v2 тот же
байт выбирает набор раундовых ключей и масок, а ответ вычисляется из случайного
128-байтного SAP — поэтому фиксированного вектора ответа v2 не существует.

## 3. Обмен v2 (проверенная структура)

Framing тот же, что у v3: `FPLY | major | minor | type | 00 | body_len:u32BE | body`.
У v2 `major = 0x02`, `minor = 0x01`.

| Сообщение | Размер | Поля |
|---|---:|---|
| M1 (клиент → приёмник) | 16 | `02 00 mode bb` в теле (offset 12..16) |
| M1-ответ | 142 | `02 mode` + 128 байт зашифрованного receiver SAP |
| M2 (клиент → приёмник) | 164 | `mode` (offset 12), `8f 1a 9c` (13..16), 128 байт зашифрованного sender SAP (16..144), 20 байт HMAC-SHA1 (144..164) |
| M2-ответ | 32 | `FPLY 02 01 04 00 | 00 00 00 14` + те же 20 байт confirmation |
| `ekey` в SETUP | 72 | `FPLY 01 02 01 00`, `len=60` (8..12), `0` (12..16), 16-байтная маска (16..32), `16` (32..36), 20 байт HMAC (36..56), 16 байт AES-ECB ciphertext (56..72) |

Проверки, которые референсная реализация выполняет до любой криптографии
(их можно реализовать уже сейчас, они не требуют констант):

- M1: `type = 1`, `body_len = 4`, `byte[12] = 2`, `byte[13] = 0`, `byte[14] < 4`, `byte[15] = 0xbb`.
- M2: `type = 3`, `body_len = 152`, `byte[12]` совпадает с mode из M1,
  `byte[13..16] = 8f 1a 9c`, и M1 уже был обработан.
- `ekey`: сигнатура `FPLY 01 02 01 00`, `len = 60`, поле 12..16 равно нулю,
  поле 32..36 равно 16.

Состояние на соединение: `mode`, «M1 обработан», «M2 принят». v2 и v3 не
смешиваются в одной сессии: v3 M2 после v2 M1 и наоборот — ошибка.

## 4. Что требуется для криптографии

Структура (RE-CODE, пригодна к независимой реализации):

- receiver SAP: 128 байт, `[0] = 0`, `[1] = 1`, остальные 126 — случайные.
- Преобразование SAP: 8 блоков по 16 байт, AES-128 (10 раундов) с цепочкой
  `state ^= previous ^ chain_mask` для блоков после первого, плюс входная и
  выходная маски на блок; расшифрование — обратный порядок.
- `mac_key` = SHA1(`mac_prefix` ‖ sender_sap ‖ receiver_sap ‖ `mac_suffix`), 20 байт.
- `wrapping_key` = MD5(`wrapping_prefix` ‖ sender_sap ‖ receiver_sap ‖ `wrapping_suffix`), 16 байт.
- confirmation = HMAC-SHA1(`mac_key`, `{0x02, 0x02}`), 20 байт.
- распаковка `ekey`: `recovered = AES-128-ECB-dec(wrapping_key, ekey[56..72]) XOR ekey[16..32]`;
  HMAC-SHA1(`mac_key`, `ekey[0..36] ‖ recovered`) должен совпасть с `ekey[36..56]`;
  результат `recovered` — 16-байтный ключ потока.

**Блокер:** значения, без которых это не работает, — 4 набора по 11 раундовых
ключей (44 × 16 байт), три набора масок по 4 × 16 байт и четыре ASCII-строки
prefix/suffix. Они не выводятся из wire-наблюдений: это результат whitebox-трассировки
Apple CoreFP, опубликованный только внутри сторонней реализации. Перенос этих
значений (даже с собственным кодом вокруг) — это перенос производного материала,
а не «wire-факт». Нужно отдельное решение владельца проекта (см. §9).

## 5. Границы: что нельзя смешивать

- **v2 ≠ mode 2 внутри v3** — см. §2. Проверять `byte[4]`, а не `byte[14]`.
- **Приёмник ≠ sender SAP.** Наш `crates/fairplay` — сторона приёмника: отвечает
  на `fp-setup` и распаковывает `ekey`. Отправительская сторона (наш будущий TX,
  UxPlay в роли sender) использует те же записи FPLY, но другие роли, ключи и
  порядок; её поведение ничего не доказывает про приём v2.
- **FairPlay handshake ≠ DRM контента.** `fp-setup`/`ekey` защищают транспортный
  ключ потока. FairPlay Streaming (CKC, лицензии, защищённое видео) — другой
  профиль; успешный v2 не даёт воспроизведения DRM-контента.
- **AP1 ≠ AP2.** macOS Music, по наблюдениям, приходит на RAOP-порт и делает
  `ANNOUNCE` (AP1), а не plist `SETUP` AP2. У нас AP1 RX нет.

## 7. Тестовые векторы: что есть и чего нет

Есть (используются в тестах этой ветки):

- три M1-сообщения из таблицы §2 — точные байты;
- префикс захваченного ответа v3 mode 1: `46 50 4c 59 03 01 02 00 00 00 00 82 02 01 cf`.

Нет:

- M1-ответ v2 — зависит от случайного receiver SAP, поэтому нужен либо захват
  пары «M1 → ответ», либо эталонная реализация для дифференциальной сверки;
- M2 v2 (164 байта) и M2-ответ (32 байта);
- `ekey` v2 (72 байта) и получившийся 16-байтный ключ;
- подтверждение, что полученный ключ действительно расшифровывает медиапоток.

Без M2 и `ekey` нельзя проверить ни одну реализацию: M1-ответ проверяется только
структурно (FPLY, версия, mode, длина 142).

## 8. План захвата с Mac

Цель — получить датированный, обезличенный набор v2-векторов и проверить, каким
путём идёт macOS Music. Захват требует отдельного согласия владельца техники.

0. **Зафиксировать контекст**: версия macOS и Music (`sw_vers`, Music → «О программе»),
   модель Mac, наш бинарник (commit + профиль), что рекламируем (`/info`, TXT),
   выбранный приёмник. Без этого захват непригоден.
1. **Запустить приёмник** с `--audio null`, `--no-mdns` не использовать (нужно
   объявление), PIN/transient по текущей политике, лог в файл.
2. **Снять трафик на Mac**:
   ```sh
   sudo tcpdump -i en0 -s 0 -w fp-v2.pcap 'tcp port 7000 or udp port 7000'
   ```
   (порт — фактический из объявления, не обязательно 7000).
3. **Воспроизвести**: Music → выбрать приёмник → Play 10–15 с → Pause → Stop.
   Повторить три раза в одной сессии и один раз после перезапуска Music.
4. **Извлечь тела** `POST /fp-setup` (M1 и M2) и plist `SETUP`/`ANNOUNCE` с
   `ekey`/`eiv`. На этом этапе трафик ещё не зашифрован — тела видны целиком.
5. **Сохранить**: pcap, извлечённые тела (hex), `/info` и TXT, лог приёмника,
   версии, дату. Приватные идентификаторы (`pi`, `pk`, `gid`, MAC) — вырезать
   или заменить; сами ключи в публичный репозиторий не кладём.
6. **Критерии приёмки захвата**:
   - есть M1 с `byte[4] = 0x02` и `byte[14]` (mode);
   - есть соответствующий M1-ответ 142 байта;
   - есть M2 164 байта и ответ 32 байта;
   - есть `ekey` 72 байта из `SETUP`;
   - зафиксировано, был ли `ANNOUNCE` (AP1) или plist `SETUP` (AP2).

Дополнительно полезно: тот же прогон с iPhone на тот же приёмник — чтобы иметь
пару v3-векторов из той же сети и той же даты для дифференциальной сверки.

## 9. План реализации и необходимое решение

| Этап | Что | Блокер |
|---|---|---|
| 1 | Явная диагностика v2 и регрессия v3 (сделано в этой ветке) | — |
| 2 | Разбор FPLY-записей v2 и проверки полей из §3 | — |
| 3 | Состояние сессии: v2/v3 не смешиваются, mode фиксируется из M1 | — |
| 4 | Преобразование SAP, `mac_key`, `wrapping_key`, confirmation | **константы §4** |
| 5 | Распаковка `ekey` v2 и подключение к `SETUP` | этап 4 |
| 6 | AP1 RX (`ANNOUNCE`/SDP/RTP) — иначе macOS Music не заиграет | отдельная задача |
| 7 | Проверка на Mac: музыка играет, ключ совпадает, v3 не сломан | Mac + согласие |

Решение, которое требуется от владельца проекта (одно из трёх):

1. сохранить §0.5 и ждать независимой деривации констант — этапы 2–3 можно
   сделать сразу, 4–5 остаются заблокированными;
2. явно разрешить перенос производных констант с provenance-тегом
   (LGPL-2.1+, автор omarroth) и атрибуцией — тогда этапы 4–5 реализуемы,
   но это исключение из действующей политики;
3. реализовать этапы 2–3 и отвечать на v2 явным `501`, пока нет решения.

## 10. Что сделано в этой ветке

- `fairplay::Error::UnsupportedV2` — v2 (`byte[4] == 0x02`) отличается от
  «неизвестной версии»; в лог попадает точная причина, ответ по-прежнему 400.
- Тесты: точные M1 macOS Music и M2-образец отклоняются именно как v2;
  v3 для всех четырёх mode по-прежнему отдаёт 142 байта с неизменным заголовком;
  v3 M2 по-прежнему отдаёт 32 байта; префикс ответа v3 mode 1 сверен с захватом;
  диспетчеризация по длине и прежние ошибки (`Length`, `Version`) сохранены.
- v3-путь (`REPLY_MESSAGE`, `FP_HEADER`, `decrypt`) не изменялся.

## 11. Ограничения

- На Mac ничего не проверялось; совместимость с macOS Music не подтверждена
  и не заявляется.
- v2-криптография не реализована: нет констант без нарушения §0.5.
- AP1 RX в ядре отсутствует, поэтому даже полный v2 не завершит путь macOS Music.
- Buffered103/`et`-политика и выбор пути AP1/AP2 клиентом не исследованы в этой
  работе; `et=5`-only поведение из issue #570 не воспроизводилось.
