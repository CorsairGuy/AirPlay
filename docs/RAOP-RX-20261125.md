# RAOP-приёмник (AirPlay 1): ANNOUNCE → SETUP → RECORD

> Историческая заметка о реализации. Сведения о базе ветки и тестах ниже относятся к моменту написания; текущее состояние — в [STATUS](STATUS.md).

Ветка `feat/raop-rx` от `main` (`847fe38`), на дату заметки ещё не влита. Реализован classic
аудиопрофиль RAOP в существующей медиачасти, без второго движка сессий и без
изменений PTP, FairPlay, HLS и Windows-интерфейса.

## Что реализовано

| Шаг | Где | Поведение |
|---|---|---|
| `ANNOUNCE` + `application/sdp` | `services/media/src/raop.rs` | Разбор `m=audio`/`a=rtpmap`/`a=fmtp`; формат сохраняется для `SETUP`. |
| `SETUP` + `Transport` | там же | Только `RTP/AVP/UDP`, `mode=record`. Занимаются порты звука, управления и времени, ответ — `server_port`, `control_port`, `timing_port`, `Session`. |
| `RECORD` | `services/media/src/rx.rs` | 200; воспроизведение начинается с первого принятого RTP-пакета. |
| RTP-звук | `crates/audio_stream/src/net.rs` | `Stream::raop`: открытый payload (`StreamKey::Plain`), общий `Playout`, существующие декодеры ALAC/PCM/AAC. |
| Timing | `crates/audio_stream/src/net.rs` | Общий NTP-сервис использует `timing_port` отправителя для активных запросов `0xD2`, принимает только соответствующие ответы `0xD3` и отдаёт часы playout; без подтверждённых свежих данных используется fallback. |
| Синхро/retransmit | существующий `receive_control` | `0xD4` задаёт anchor, `0xD6` возвращает повторно присланный пакет. |
| Громкость | существующий `set_parameter` | `volume: dB` из `text/parameters`, чтение через `GET_PARAMETER`. |
| `FLUSH` | `services/media/src/rx.rs`, `Playout::clear` | При `RTP-Info` весь буфер отправителя объявляется недействительным, вывод останавливается, поток продолжает жить. |
| `TEARDOWN` | существующий путь | Освобождает поток; следующий `SETUP` снова требует `ANNOUNCE`. |

Согласованные форматы: ALAC (`AppleLossless`, параметры из `fmtp`: frameLength,
bitDepth 16/24, каналы 1–2, sampleRate), `L16` (PCM S16BE) и `mpeg4-generic`
(AAC-LC). Неподдержанный кодек отклоняется на `ANNOUNCE` с 415, а не
подтверждается и не превращается в тишину.

## Что отклоняется явно

- **`rsaaeskey` / `fpaeskey` / `aesiv`, а также `et` без открытого режима — 501 на ANNOUNCE.**
  Шифрованный RX пока не реализован; RSA и FairPlay не следует считать одним и тем же способом обмена ключами.
- **RTP-over-RTSP (`RTP/AVP/TCP`) — 501.** Поддерживается UDP-профиль. Параметр `interleaved` внутри `RTP/AVP/UDP` допускается: такое сочетание отправляет OwnTone (ревизия `612d6b3cf34ae38bb71b6edfcd69fd7afe6ab25c`); фактический транспорт остаётся UDP.
- **`mode` не `record`, отсутствие `RTP/AVP`, пустой `Transport` — 400/501.**

После исходной заметки добавлены запросы пересылки потерянных пакетов (`0x55`); аппаратная проверка открыта. Не реализованы DACP/Active-Remote, повторное шифрование/декодирование AAC-ELD.

Для RAOP TX `crates/crypto/src/raop.rs` использует протокольный публичный RSA-модуль длиной 256 байт (2048 бит), экспоненту 65537 и OAEP/SHA-1. 1024-битный ключ в unit-тесте — отдельная синтетическая пара, а не размер протокольного ключа. AES-CBC примитив проверен векторами; это не означает наличие расшифровки защищённого RX или проверки реального устройства. Отчёт ветки `feat/c68-raop-rx-crypto` ошибочно называл протокольный модуль 1024-битным и не перенесён без исправлений.

## Тесты

MSYS2/GNU, `cargo test --offline -p audio_stream -p media -p sessions`:

- `audio_stream`: 4 теста, включая открытый payload и ответ времени (origin
  эхо, метки не нулевые, `0xD4` не принимается за запрос времени).
- `media`: 79 тестов, включая разбор SDP для ALAC 16/24 бит, PCM и AAC,
  отклонение зашифрованного профиля и неподдержанных параметров, профили
  `Transport`.
- `sessions`: 23 теста, включая `raop_end_to_end_plays_alac`: синтетический
  отправитель делает ANNOUNCE → UDP SETUP → RECORD, присылает два RTP-пакета
  с известным ALAC без сжатия, и в выводе (`audio::Sink`) появляется
  проверяемая последовательность PCM `10, -10, 20, -20, 30, -30`; затем
  проверяются громкость `-20 дБ`, `FLUSH` и освобождение потока.

`cargo clippy --offline -p audio_stream -p media -p sessions --all-targets` —
без новых предупреждений (остались только прежние предупреждения манифеста).

## Непроверенное и план аппаратной проверки

Реальный iPhone/iTunes/macOS Music не подключался; заявлений о совместимости
нет. Для проверки нужно:

1. Захватить `ANNOUNCE`/`SETUP` реального отправителя и зафиксировать
   `Content-Type`, `Transport`, `et`, наличие `rsaaeskey` (обычно есть — тогда
   потребуется отдельная задача про RSA-ключ приёмника).
2. Проверить, что отправитель принимает наши `server_port`/`control_port`/
   `timing_port` и шлёт `0xD2` на timing-порт; ответ `0xD3` должен учитываться
   в его логе.
3. Снять фактический формат (`fmtp`, SSRC, payload type) и убедиться, что
   декодированный PCM совпадает с эталонной записью, а громкость и `FLUSH`
   слышны.
4. Отдельно проверить потерю пакетов: сейчас пересылку мы не запрашиваем.

## Timing после интеграции

RAOP использует общий `timesync::ntp`, а не отдельный пассивный оценщик. `SETUP` передаёт объявленный `timing_port`; запросы и ответы проверяются по адресу, а ответ — также по порту, origin и сроку ожидаемого запроса. Устаревший offset больше не используется. Проверены loopback и отказы чужих/несовпадающих ответов; на реальном AirPlay 1-устройстве, при потере пакетов и длительном воспроизведении ещё не проверялось. Если порт отсутствует, остаётся fallback.
