# Тестовый прогон: iPhone ↔ Windows, без HomePod и Apple TV

Ветка `review/today-20261127` (база — `main` `08a2ff3`), 27 ноября 2026.
Документ описывает ровно то, что координатор запускает автоматически, и то,
что пользователь проверяет руками между iPhone и Windows.

Стенд намеренно узкий: **один iPhone как отправитель, Windows как приёмник**.
Группы/HomePod, Apple TV, зеркалирование, видео, HLS и фото в этот прогон не
входят — для них нужен отдельный стенд и отдельные ожидания.

## 1. Что запускает координатор

```bash
./scripts/verify-today.sh          # линт + тесты + interop
./scripts/verify-today.sh quick    # линт + тесты
OFFLINE=1 ./scripts/verify-today.sh
```

Скрипт печатает `=== <команда>` перед каждым шагом, `!!! FAILED` при падении и
итог в конце; код возврата ненулевой, если упал хотя бы один шаг. Ничего не
устанавливает и не меняет.

Состав прогона и что он доказывает:

| Шаг | Проверяет | Чего не доказывает |
|---|---|---|
| `cargo fmt --all --check` | форматирование после слияний | — |
| `cargo clippy --workspace --all-targets -- -D warnings` | предупреждения во всех целях | поведение на устройстве |
| `cargo test -p clock -p timesync -p audio_stream -p media` | ядро сегодняшних правок: аттестация часов, NQPTP SHM, эпоха RTP, вывод звука, приём медиа | реальные часы и звук |
| `cargo test --workspace` | остальные крейты после слияний | FFmpeg-профиль, ARM |
| `cargo test -p runtime --no-default-features` | аудио-профиль без видео и зеркалирования | — |
| `cargo test -p runtime --features mirroring` | правки общего кода не сломали зеркалирование | само зеркалирование на Apple TV |
| `interop_receiver` + `tests/interop/pyatv_client.py` | независимый клиент: сопряжение, шифрованный RTSP, MRP-кадры | iPhone и слышимый звук |

Требования для interop-шага: Python 3.11+ и
`pip install "pyatv==0.14.5" "srptools==1.0.1"`. Если их нет, шаг печатает
`SKIP` — это не падение, но и не пройденная проверка.

Ожидаемые результаты: каждый `cargo test` заканчивается `test result: ok`
без `FAILED`; clippy молчит; interop печатает успешный итог клиента.

## 2. Что проверяет пользователь: iPhone → Windows

### 2.1 Подготовка Windows

1. Rust stable (`rust-toolchain.toml`), Git Bash.
2. Сборка аудио-профиля и харнесса:

   ```bash
   cargo build -p runtime --no-default-features --example interop_receiver
   ```

3. Запуск приёмника с видимостью в AirPlay-меню и реальным выводом звука:

   ```bash
   RUST_LOG=info ./target/debug/examples/interop_receiver \
       --mdns --device default --name "AirPlay-Win" --port 7123 --pin 1234 \
       --state-dir ./state
   ```

   `--mdns` публикует `_airplay._tcp` через Bonjour, поэтому iPhone видит
   приёмник в списке. `--device default` открывает вывод через `cpal`
   (WASAPI на Windows); `--device null` — тишина, темп реального времени.
   Без `--mdns` харнесс работает только для pyatv по указанному порту.

4. Если iPhone просит код — `1234`. Состояние сопряжения лежит в `--state-dir`,
   повторный запуск с той же папкой не должен требовать PIN заново.

Порт 7123 должен быть доступен: правило брандмауэра для `interop_receiver.exe`
разрешить в частной сети. Не открывать порт в общедоступный профиль.

### 2.2 Сценарии

Отмечать PASS/FAIL/PARTIAL/TODO и прикладывать `receiver.log`. Ничего не
менять в прошивках, роутере и настройках iPhone между шагами.

| ID | Действие | Критерий | Что смотреть |
|---|---|---|---|
| W01 | iPhone → «AirPlay-Win» в AirPlay-меню | Приёмник виден; подключение без PIN или с `1234`; в журнале есть SETUP и старт сессии | discovery, RTSP SETUP |
| W02 | Воспроизведение трека (Apple Music / Яндекс Музыка) | Звук идёт без провалов и щелчков, старт за доли секунды | `декодер`, `воспроизведение` |
| W03 | Пауза 5 с → Play ×3 | Трек не начинается заново, обложка/позиция не скачут | пауза/`FLUSH`, `epoch` |
| W04 | Seek +20 с и −20 с | Звук переходит на новую позицию, без «зависания навсегда» и без старого PCM | `FLUSH`, `played_through` |
| W05 | Next/Prev трек | Новый трек играет, старая шкала меток не блокирует новую | смена эпохи/якоря |
| W06 | Ползунок громкости iPhone | Громкость меняется без разрыва сессии | `apply_volume` |
| W07 | Отключиться и подключиться снова | Приёмник остаётся в меню, новая сессия стартует, старая не висит | teardown/reconnect |
| W08 | Wi-Fi на iPhone выключить на 5 с и включить | После возврата либо восстановление, либо понятный отказ; зависания и «тишина навсегда» без журнала недопустимы | переякорение, `resyncs` |
| W09 | 10–15 минут непрерывного воспроизведения | Нет роста памяти, нет дрейфа в виде периодических рывков | RSS процесса; при `RUST_LOG=debug` — `буфер переполнен` |
| W10 | Проверить, что в AirPlay-меню **не** выбраны HomePod и Apple TV | Звук идёт только на Windows; группа не создаётся | — |

### 2.3 Что именно проверяет этот стенд

- **W02–W06** — приём медиа (`services/media/src/rx.rs`) и вывод
  (`crates/audio_stream/src/playout.rs`): буфер, декодер, якоря, `FLUSH`,
  подстройка частоты кадрами.
- **W07–W08** — жизненный цикл сессии и поведение шкалы меток при потере
  отправителя. Эвристика новой эпохи (`Config::allow_heuristic_rtp_recovery`)
  по умолчанию **выключена**, поэтому W08 проверяет штатное восстановление, а
  не эвристику: подтверждённый перезапуск отправителя без `FLUSH` может
  потребовать переподключения — это известное ограничение, а не дефект прогона.
- **W09** — пределы очереди (`MAX_BUFFERED_PACKETS`) и отсутствие утечек.
- **W03/W04** — что `FLUSH` трактуется как граница отброса (как в
  shairport-sync), а не как объявление новой шкалы.

### 2.4 Что этот стенд не проверяет

- **HomePod / группы**: мультирум, `group_latency_offset_ns`, ретрансляция,
  общая синхронизация нескольких выходов. Нужен отдельный стенд.
- **Apple TV**: зеркалирование, MRP-пульт, companion, видео, HLS, фото.
  В профиле `--no-default-features` этих зависимостей нет вообще.
- **PTP и NQPTP**: харнесс стартует с `TimeSync::idle` и `features & !PTP`,
  то есть без grandmaster/follower. Чтение SHM и аттестация часов покрыты
  только unit-тестами `crates/clock`.
- **Побитовая точность**: `cpal` на Windows обычно отдаёт 48 кГц, поэтому
  вывод ресемплируется линейной интерполяцией. Совпадение «сэмпл в сэмпл» этим
  прогоном не проверяется и не должно заявляться.

### 2.5 Журнал результата

На каждый прогон приложить: дату, коммит ветки, версию iPhone/iOS, приложение
источника, `receiver.log` уровня `info`, отметки PASS/FAIL по W01–W10 и
описание слышимого поведения. PIN, ключи сопряжения и токены в журнал не
попадают: `--state-dir` содержит ключи, его не прикладывать.
