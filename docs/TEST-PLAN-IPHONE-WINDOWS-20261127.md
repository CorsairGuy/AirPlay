# Ручной прогон: iPhone → Windows

Один отправитель (iPhone) и один приёмник (Windows). Всё остальное — вне
стенда. План не дублирует `AGENT-TASKS.md`: статусы и ограничения задач там,
здесь только то, что запускает координатор и что проверяет пользователь.

## 1. Что запускает координатор

Автоматическая часть — команды из CI-задания `interop-pyatv`
(`.github/workflows/ci.yml`), вручную:

```bash
cargo test --offline -p timesync --lib     # часы и маршрут relay
cargo fmt --all --check
cargo clippy --offline --workspace --all-targets -- -D warnings

pip install "pyatv==0.14.5" "srptools==1.0.1"
cargo build -p runtime --example interop_receiver
./target/debug/examples/interop_receiver --port 7123 --pin 1234 \
    --state-dir "$(mktemp -d)" > receiver.log 2>&1 &
python tests/interop/pyatv_client.py 127.0.0.1 7123 1234
```

`pyatv_client.py` проверяет независимым клиентом `/info`, pairing
(PIN/transient/legacy), verify и MRP-кадры. Он **не** проверяет звук и не
заменяет iPhone.

Здесь ничего из этого не запускалось: `cargo`/`rustc` в окружении агента нет,
установка запрещена. Числа тестов и зелёный clippy — не подтверждены.

## 2. Что проверяет пользователь

### 2.1 Подготовка Windows

1. Rust stable по `rust-toolchain.toml`, Git Bash или PowerShell.
2. Сборка приёмника с видимостью в AirPlay-меню и реальным выводом звука:

   ```bash
   cargo build -p runtime --example interop_receiver
   RUST_LOG=info ./target/debug/examples/interop_receiver \
       --mdns --device default --name "AirPlay-Win" --port 7123 --pin 1234 \
       --state-dir ./state
   ```

   `--mdns` поднимает Bonjour-объявление (`_airplay._tcp`/`_raop._tcp`), поэтому iPhone видит приёмник в списке;
   без него харнесс доступен только по адресу и порту. `--device default`
   открывает вывод через `cpal` (WASAPI), `--device null` — тишина в темпе
   реального времени. Приёмник печатает `READY <port>`.
   Вариант только-аудио: собрать с `--no-default-features` (без mirroring).

3. Правило брандмауэра для `interop_receiver.exe` — только частная сеть,
   порт 7123. В общедоступный профиль не открывать.
4. PIN задан `1234`, но харнесс стартует с `require_pin: false`, то есть
   подключение может пройти и без кода; состояние сопряжения лежит в
   `--state-dir`, повторный запуск с той же папкой не должен требовать пары
   заново.

### 2.2 Текущее состояние (27 ноября 2026)

Уже подтверждено: объявление видно, если процессу разрешён доступ к локальной
сети; transient pairing и зашифрованный RTSP проходят. **Звук не запустился**:
в одной попытке audio SETUP отклонён проверкой `shk`, в другой сессия
закрылась после NTP SETUP до audio SETUP. Поэтому W02–W10 сейчас ожидаемо
падают, и цель прогона — не «всё зелёное», а журнал с точным местом отказа.
Подробности и статус — C27 в [AGENT-TASKS](AGENT-TASKS.md).

### 2.3 Сценарии

Отмечать PASS / FAIL / PARTIAL / BLOCKED, прикладывать `receiver.log` уровня
`info` (при разборе отказа — `debug`). Между шагами не менять настройки
iPhone, роутера и прошивки.

| ID | Действие | Критерий | Что смотреть в журнале |
|---|---|---|---|
| W01 | iPhone → «AirPlay-Win» в меню AirPlay | Приёмник виден; подключение с `1234` или transient; есть SETUP и старт сессии | `SETUP`, `pair`, порт |
| W02 | Воспроизведение трека | Звук без провалов и щелчков, старт за доли секунды | `audio SETUP`, `shk`, `декодер`, `воспроизведение` |
| W03 | Пауза 5 с → Play ×3 | Трек не начинается заново, позиция не скачет | пауза, `FLUSH`, эпоха |
| W04 | Seek +20 с и −20 с | Переход на новую позицию без «зависания навсегда» и без старого PCM | `FLUSH`, `played_through` |
| W05 | Next/Prev трек | Новый трек играет, старая шкала меток не блокирует новую | смена якоря/эпохи |
| W06 | Ползунок громкости iPhone | Громкость меняется без разрыва сессии | `apply_volume` |
| W07 | Отключиться и подключиться снова | Приёмник остаётся в меню, новая сессия стартует, старая не висит | teardown, повторный SETUP |
| W08 | Wi-Fi на iPhone выключить на 5 с и включить | Либо восстановление, либо понятный отказ; «тишина навсегда» без журнала недопустима | переякорение, `resyncs` |
| W09 | 10–15 минут непрерывного воспроизведения | Нет роста памяти и периодических рывков | RSS процесса, `буфер переполнен` |
| W10 | В меню **не** выбраны HomePod и Apple TV | Звук идёт только на Windows, группа не создаётся | — |

### 2.4 Границы стенда

- **HomePod / группы, Apple TV, зеркалирование, видео, HLS, фото** — не этот
  стенд: нужны отдельные устройства и ожидания.
- **PTP и NQPTP** — харнесс стартует без PTP (`features & !PTP`), внешний
  NQPTP в ядро не встраивается. Часы проверяются unit-тестами, не здесь.
- **Побитовая точность** — `cpal` на Windows обычно отдаёт 48 кГц, вывод
  ресемплируется; совпадение «сэмпл в сэмпл» не проверяется и не заявляется.
- **Windows-приложение** — харнесс это пример ядра, а не интерфейс приложения.
