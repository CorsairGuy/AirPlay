# Discovery и выбор профиля AirPlay-получателя

Ветка `feat/discovery-profiles`, база — актуальный `main` (`847fe38`).
Изменения не влиты в `main`.

## Что изменено

### Таблица служб

`crates/mdns/src/discovery.rs`:

- `Kind::Both` и `Browser::start_all()`: `_airplay._tcp` и `_raop._tcp` слушаются
  одним браузером, события двух потоков сводятся в один `feed`.
- `ServiceTable` хранит обе службы. Ключ записи — (тип, полное имя, хост),
  поэтому:
  - записи `_airplay` и `_raop` одного устройства не затирают друг друга;
  - одинаково названные колонки на разных хостах остаются двумя записями;
  - повторный resolved-пакет с новым адресом заменяет запись на месте, а не
    добавляет вторую;
  - `ServiceRemoved` удаляет только записи своего типа и имени, второй тип
    устройства остаётся.
- Одиночные `Kind::AirPlay`/`Kind::Raop` сохранены: для них таблица по-прежнему
  игнорирует чужой тип.

### Возможности и профиль

`services/discovery/src/capabilities.rs` — новый слой поверх той же таблицы,
без второго каталога устройств:

- записи группируются по MAC (`deviceid` AirPlay или префикс имени RAOP
  `MAC@Name`); группы без MAC не сливаются по имени, чтобы не угадывать;
- разбираются `features` двумя словами (`0xНИЗ,0xВЕРХ`), `flags`, `model`,
  `srcvers`, `at`, RAOP `ch`/`sr`/`ft`/`et`/`pw`;
- биты: 9 — звук, 7 — экран, 14 — FairPlay, 40 — buffered audio, 41 — PTP,
  46/47/48 — заявленные виды сопряжения;
- `realtime` не выводится из TXT и остаётся `None`: режим подтверждает только
  SETUP;
- неизвестное поле — `None`, а расхождение записей одного устройства по
  `features`/`flags` — конфликт, при котором профиль не выбирается;
- сохраняются все адреса IPv4 и IPv6 со scope id; «первый» адрес не выбирается.

`capabilities::select(&Device, Want)` и `select_for_output(table, catalog, uid,
Want)` возвращают либо `Start { profile, notes }`, либо `Refuse { code, reason }`.

## Какие профили выбираются автоматически

| Данные получателя | Звук (`Want::Audio`) | Экран (`Want::Screen`) |
| --- | --- | --- |
| `_airplay` с `features`, бит 9 = 1 | AirPlay 2 realtime audio | отказ: бит 7 не выставлен |
| `_airplay` с `features`, бит 9 = 1, бит 7 = 1 | AirPlay 2 realtime audio | отказ: отправителя зеркалирования нет в этой сборке |
| только `_raop` | отказ: RAOP-отправителя нет | отказ |
| `features` нет / не разобраны | отказ: профиль неизвестен | отказ |
| `features` расходятся между записями | отказ: противоречивые объявления | отказ |
| RAOP `pw` требует пароль | отказ: поддерживается только PIN | — |
| бит 41 (PTP) | AirPlay 2 realtime audio, в notes — NTP-тайминг через SETUP | — |

Единственный реально поддерживаемый профиль — `AirPlay2RealtimeAudio`; это
существующий отправитель `media::tx::Session`. Зеркалирование в этой сборке
отправителя не имеет, поэтому даже при бите 7 возвращается `SenderUnavailable`,
а не запуск неподдерживаемого потока.

Точка входа `media::tx::run_selected_discovered` сначала проверяет профиль для
каждой выбранной логической строки и только потом открывает соединения. Старый
`run_selected` оставлен без изменений для вызывающих, у которых нет таблицы
discovery.

## Что остаётся неизвестным

- **Realtime/buffered фактически**: TXT даёт только бит 40 (buffered). Ответ
  SETUP на realtime-поток не проверяется до сессии.
- **Кодеки и форматы**: `ft`/`sr`/`ch` RAOP сохраняются как объявленные числа,
  без перевода в список кодеков; AP2-кодеки в TXT не объявляются.
- **Требования pairing**: биты 46/47/48 означают заявленные возможности, а не
  требование; `pw` — единственный явно разобранный признак пароля.
- **PTP**: бит 41 только фиксируется. Сессия по-прежнему согласует NTP, движок
  PTP не настраивался и не менялся.
- **Адрес для подключения**: сохраняются все IPv4/IPv6; выбор интерфейса
  остаётся за вызывающим, как и раньше.

## Проверки

- `cargo test -p mdns -p discovery -p airplay --offline` — все тесты прошли
  (включая 8 новых тестов возможностей и 3 новых теста таблицы служб).
- `cargo clippy --workspace --all-targets --offline -- -D warnings` — без
  ошибок.
- Покрыто тестами: TXT по структуре Apple TV, объединение `_airplay`+`_raop`
  по MAC, IPv4/IPv6 одновременно, неполный TXT, противоречивые `features`,
  RAOP-only, пароль RAOP, одинаковые имена на разных хостах, обновление адреса,
  удаление одного типа и сохранение второго.

**С реальными устройствами не проверялось**: в окружении нет AirPlay-приёмников,
поэтому сетевой обмен, ответы SETUP и фактический выбор realtime/buffered
остаются непроверенными.
