# Несколько независимых AirPlay-профилей в одном процессе — 25.11.2026

> Историческая заметка о реализации. Сведения о базе ветки и тестах ниже относятся к моменту написания; текущее состояние — в [STATUS](STATUS.md).

Ветка `feat/multi-profile` от актуального `origin/main` (`847fe38`).
Задача: API ядра для нескольких экземпляров приёмника со своими именем,
профилем, identity и настройками; независимый жизненный цикл; тесты двух
экземпляров. Windows-интерфейс и Станция не тронуты; PTP-движок не изменён.

## 1. Что мешало раньше (аудит)

| Ресурс | Где жил | Следствие для нескольких экземпляров |
|---|---|---|
| Точка входа | `serve::run(opts)` сам занимал порт и ждал Ctrl-C | Один экземпляр на процесс; остановка означала выход из процесса |
| Соединения | `transport::accept_loop` порождал задачи отсоединённо | Остановка одного экземпляра не закрывала его соединения |
| Identity | `state::load_identity(state_dir)`, `device_id` из seed | Свой ключ на каталог; общий каталог — общая identity |
| Pairings | `FileStore` в том же каталоге, `Mutex` внутри | Два экземпляра в одном каталоге пишут без межпроцессной блокировки |
| Порты RTSP | `Options::port` | Свой у каждого; несколько экземпляров можно развести по портам |
| PTP | `TimeSync::start()` занимает 319/320; при неудаче только `warn!` | Второй экземпляр молча остаётся без слушателя |
| mDNS | `Advertiser` на экземпляр; host из `device_id`, instance из имени | Регистрации независимы, но два демона в одном процессе не проверены |
| Сессии | `Context` (identity, device, store, player, mdns, mirror, remote, mrp, session_group) | Уже свой у каждого вызова; общих изменяемых полей нет |
| Аудио/видео | `Player` и фабрика видео в `Options` | Свой вывод у каждого; физическое устройство делит приложение |
| Глобальные | `random_pgid` на запуск; `ntp::base_ns` — `OnceLock` только для чтения | Безопасны: не меняются после инициализации |

## 2. API

```rust
let clock = timesync::TimeSync::start(clock_id); // один на процесс, если нужен PTP
let a = serve::start(opts_a).await?;            // Receiver
let b = serve::start(opts_b).await?;            // независимый Receiver
a.stop().await;                                 // b продолжает работать
```

- `serve::start(Options) -> Result<Receiver>` — поднимает экземпляр и сразу
  возвращает ручку; не блокирует поток и не ставит обработчик Ctrl-C.
- `Receiver::name()`, `device_id()`, `port()`, `device()` — для диагностики и
  тестов; `Receiver::stop()` — закрывает приём, соединения и снимает mDNS;
  `Drop` без `stop` обрывает соединения в фоне.
- `serve::run(Options)` остался для CLI: `start` + ожидание Ctrl-C + `stop`.
- Профиль задаётся снаружи через поля `Options`: `name`, `model`, `features`,
  `status_flags`, `accessory_type`, `source_version`, `enclosure_color`,
  `display`, `audio`, `mirror`/`hls`, `state_dir` (identity), `port`, `mdns`,
  `mrp`, `events`, `remote`.
- Identity: один `state_dir` — один ключ и один список pairings. Разные
  профили — разные каталоги; общий каталог даёт одну identity на всех.
- PTP: новое поле `Options::time: Option<TimeSync>`. `None` — как раньше,
  экземпляр заводит свой движок. Если экземпляров несколько и им нужен бит
  41, приложение создаёт `TimeSync` один раз и передаёт клоны: движок и
  сокеты 319/320 общие, а identity, порт и сессии остаются раздельными.
  Это отдельная точка интеграции; сам движок не менялся.

## 3. Изменения в коде

- `services/sessions/src/transport.rs`: `accept_loop(..., shutdown:
  watch::Receiver<bool>)`; соединения экземпляра живут в его `JoinSet` и
  закрываются при остановке, не задевая чужие.
- `bin/airplay/src/sessions/serve.rs`: `Receiver`, `start()`, `stop()`,
  `Drop`; `run()` выражен через них; `Options::time`.
- `bin/airplay/src/main.rs`: `time: None` в профиле CLI.
- `bin/airplay/tests/multi_profile.rs`: интеграционный тест.
- `README.md`, `CHANGELOG.md`: краткое описание API и ограничений.

## 4. Тесты

`cargo test -p airplay --test multi_profile` — один тест, loopback, аудио
`null`, без mDNS и без PTP-сокетов:

1. Два экземпляра на разных портах и с разными `state_dir`; `device_id`
   различаются.
2. `/info` каждого: свои `name`, `model`, `deviceID`; профили не текут.
3. Четыре одновременных подключения (по два к каждому) — все отвечают.
4. `a.stop()`: порт A закрыт, B отвечает и сохраняет свою identity.
5. Повторный запуск A с тем же каталогом: `deviceID` сохранился, B работает.
6. Общая служба времени передана клонами в оба экземпляра (точка
   интеграции PTP).

Проверки: `cargo fmt --all`, `cargo clippy --workspace --all-targets
--offline -- -D warnings`, `cargo test -p airplay -p sessions --offline` —
все зелёные.

## 5. Обнаружение с реальных Apple-устройств

**Не проверено.** Apple-устройств нет; в тесте Bonjour выключен, два
`Advertiser` в одном процессе не запускались. Поэтому не утверждаю, что
iPhone одновременно видит оба экземпляра и что два mDNS-демона на одном
хосте не мешают друг другу. Это первое, что нужно проверить на железе:
запустить два экземпляра с `mdns: true`, разными именами и `state_dir` и
посмотреть меню AirPlay на iPhone/Mac.

## 6. Ограничения и точки интеграции

- PTP: второй вызов `TimeSync::start()` не падает, а молча работает без
  слушателя (`is_listening() == false`). Для нескольких экземпляров с
  битом 41 передавайте общий `TimeSync` через `Options::time`; не заводите
  его дважды.
- mDNS: у каждого экземпляра свой демон и свои регистрации; одновременная
  работа двух демонов на одном хосте не проверена (см. §5).
- Аудио: `Player` открывает устройство из `Options::audio`; два экземпляра
  на одном физическом устройстве могут конфликтовать (эксклюзивный режим
  WASAPI/ALSA). Приложение выбирает устройства или `null`.
- `state_dir`: общий каталог даёт общую identity и общий файл pairings без
  межпроцессной блокировки; для разных профилей — разные каталоги.
- Остановка `Receiver` обрывает активные соединения экземпляра (отправитель
  видит закрытый сокет), не дожидаясь TEARDOWN. Другие экземпляры это не
  задевает.
- CLI (`serve::run`) по-прежнему один экземпляр; несколько — только через
  библиотечный `start`.
