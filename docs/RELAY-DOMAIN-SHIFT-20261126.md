# Relay: граница доменов и одиночный сдвиг метки

Ветка `feat/relay-domain-shift`, база — `main` `b612eb4`, 2026-11-26.
Задача **E** из [AGENT-TASKS](AGENT-TASKS.md) — часть «Маршрут времени
RX → relay → TX».

## Сверка с кандидатом Станции

`station-ref/docs/RELAY_TIMING_CANDIDATE.md` требует: «A single monotonic
sender clock supplies both timing replies and media timestamps… Scheduler delay
does not rewrite the epoch». В ядре это уже выполнено для исходящей ветки:
`MediaClock::packet_with_ptp` читает провайдер **один раз** в
`packet.produced`, `PtpPacketizer::packetize` проверяет домен и вызывает
`PtpPlan::anchor(rtp, mapping_lead, reading)` ровно с той же меткой, а
`mapping_lead` вычитается только в sync-пакете, не в заголовке.

Чего не хватало: **границы доменов на relay-прыжке**. Если кадр пришёл из
входящей сессии в одном домене и уходит в группу с другим, не было типа,
который (а) выполняет пересчёт один раз, (б) не даёт применить его повторно к
уже пересчитанному кадру, (в) отвергает кадр чужой сессии вместо «примерно
правильного» сдвига. Опасный случай — совпадение `clock_id` входящего и
исходящего доменов: тогда повторная штамповка неотличима от правильной и
даёт двойной сдвиг.

## Что сделано

`services/media/src/tx/relay.rs` — чистый модуль без I/O, часов и сокетов:

- `Shift::between(inbound, outbound)` — смещение между доменами по двум
  чтениям одного producer-момента. Равные домены отвергаются
  (`SameDomain`): границы нет, сдвигать нечего. Смещение, не влезающее в
  `i64`, отвергается до того, как тронута метка.
- `Shift::apply(ns)` — проверенный пересчёт; перенос за границы `u64`
  сообщается (`OutOfRange`), а не публикуется завёрнутым.
- `RelayedDeadline { ns, domain }` — метка помнит свой домен.
  `Shift::cross(deadline)` срабатывает только для метки в исходном домене,
  поэтому второе применение того же прыжка даёт `WrongSource`, а не тихий
  двойной сдвиг.

## Проверки

```
cargo test --offline -p media --lib relay  -> 5 passed
cargo test --offline -p media --lib        -> 131 passed
cargo fmt --check -p media                 -> relay.rs чист; старые raop.rs/rx.rs
                                              расходятся и на b612eb4 (не трогал)
```

Тесты: один прыжок сдвигает метку на измеренное смещение и меняет домен;
цепочка A→B→C даёт ровно тот же результат, что прямой A→C (каждая граница
один раз); повторное применение прыжка к уже пересчитанной метке и чтения из
одного домена отвергаются; метка чужой сессии отвергается; отрицательное
смещение и переполнение сообщаются, а не заворачиваются.

`clippy -p media --all-targets -D warnings` падает на `items after a test
module` в `services/media/src/tx/mirror.rs:731` — это состояние `main`, к
этому изменению не относится.

## Что осталось от E

- Сквозной loopback с **живыми** сокетами и одновременно входящим follower и
  исходящим master (часть уже покрыта тестами `ptp_group`, но не как единый
  прогон RX → relay → TX).
- pause/seek/перезапуск и invalidation при потере источника или часов на
  relay-границе; согласование receiver/hardware буферов.
- `Shift` здесь — контракт для вызывающего; сам relay-путь в
  `bin/airplay`/`services/media` его пока не использует, поэтому тип не
  доказывает, что существующий код уже безопасен.
- Аппаратной проверки нет; синхронность звука не измерялась.
