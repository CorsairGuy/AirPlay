# AirPlay: общее ядро и перенос Станции

Срез аудита: 30 октября 2026. Это план развития существующего [CorsairGuy/AirPlay](https://github.com/CorsairGuy/AirPlay), а не новая реализация с нуля. Устройства при подготовке документа не изменялись. Браузер пользователя не использовался для восстановления чата.

## Что удалось восстановить из Claude

Тред **Build AirPlay from scratch in Rust** найден в локальном HTTP-кэше приложения Claude: восстановлены 124 сообщения с точным идентификатором пользовательской ссылки. Полная локальная выгрузка сохранена в `work/claude-universal-thread/TRANSCRIPT.md`. Артефакты по ссылкам из сообщений не считаются прочитанными, если их содержимого нет в выгрузке.

Последний содержательный итог Claude: перенести hardware-independent часть `airplay_mrp` со Станции в `mrp`; оставить Алису, Glagol, Bluetooth, D-Bus, Avahi-интеграцию и управление локальными источниками в адаптере. `--mrp-bridge` уже подготовлен, перенос самого сервера MRP ещё предстоит. Последний вопрос Claude о переносе `airplay_sender` логично закрыть положительно в рамках общей задачи: протокольный отправитель нужен ядру, управление источниками Станции — адаптеру.

Уточнение аудита: поддержка моста MRP не равна готовому серверу MRP. Наблюдение `igl=1`/`gcgl=1` относится к конкретным опытам со Станцией; оно не доказывает универсальное достаточное условие работающей кнопки группировки.

## Два репозитория

**AirPlay** владеет discovery, идентичностью устройства, pairing/crypto, RTSP/RTP, кодеками, медиачасами, приёмом и передачей аудио, MRP, метаданными, состоянием группы и командами. Видео, mirroring, HLS и другие роли доступны отдельными возможностями сборки. Ядро не знает имён процессов Алисы, путей sysfs или модели колонки.

**yandex_station_airplay** владеет сборкой под устройство, установкой и откатом, ALSA/BlueZ/Glagol, получением контента Алисы, локальными приоритетами и ducking, GPIO/sysfs/подсветкой. Он подключает закреплённую версию общего ядра через публичный Rust API либо версионированный IPC. Похожим способом подключаются другие устройства.

В существующем ядре уже есть абстракции аудиовыхода `SinkFactory` и видеовыхода `FrameSink`: развивать их, а не заводить параллельный каркас. Предпочтительные имена служб из треда: `airplay`, `mediaserver`, `mediaremote`, `timesync`; не переименовывать уже существующие пакеты только ради косметики.

## Что есть сейчас

Проверенный main общего ядра: [767b1156b7d6a7176aae54bfe03a5e883f6a0320](https://github.com/CorsairGuy/AirPlay/tree/767b1156b7d6a7176aae54bfe03a5e883f6a0320).

- Есть работающий каркас Rust, discovery, pairing, AP2 audio receive paths, timing и отдельные video/mirroring пути. Есть CI и interop-проверки pairing через pyatv.
- `mrp`, `companion`, `hls`, `capture`, `ipc` и службы mediaremote/mediaserver пока содержат заглушки в проверенных точках входа. MRP bridge уже существует в приёмнике.
- Команды CLI `send/list/status/pair/set/log` пока явно сообщают, что не реализованы. Нельзя объявлять отправку и управление готовыми по наличию этих команд.
- Classic AirPlay 1 audio receive не завершён: `ANNOUNCE` возвращает 501. Legacy pairing и звук mirroring не заменяют этот режим.
- Отключение mirroring настройкой не делает сборку без видео: зависимости бинарника нужно разделять Cargo features.
- [Успешный CI](https://github.com/CorsairGuy/AirPlay/actions/runs/40932488604) доказывает перечисленные проверки, но не синхронность реальных HomePod и не отсутствие регрессий на Станции.

Матрица протокола и ссылки на проверенные исходники: [AIRPLAY-PROTOCOL.md](AIRPLAY-PROTOCOL.md).

## Как выбирать лучшие реализации

Выбирать по роли, совместимости, измерениям и лицензии. Не объединять целые деревья проектов автоматически.

| Источник | Для чего использовать | Граница переноса |
|---|---|---|
| [Shairport Sync](https://github.com/mikebrady/shairport-sync) | Зрелый audio RX baseline, lifecycle, timing, backends | Сначала эталон interop; перенос отдельных файлов после проверки notices. Основной код MIT, есть другие лицензии |
| [NQPTP](https://github.com/mikebrady/nqptp) | Clock tracking, сравнение timing | GPL-2.0-only в исходниках: не копировать бездумно в GPL3 workspace; рассмотреть отдельный процесс с проверкой интерфейса и условий распространения |
| [OwnTone](https://github.com/owntone/owntone-server) | AP1/AP2 TX и multiroom reference | Не тащить библиотеку музыки, БД и UI. Проверять зависимости выделяемого sender; соответствующий код GPL-2.0-or-later |
| [pyatv](https://github.com/postlund/pyatv) | Pairing, control, MRP schemas, независимый тестовый клиент | MIT; Python удобен для тестов, необязателен на embedded-устройстве |
| [UxPlay](https://github.com/FDH2/UxPlay) | Mirroring/video reference, дополнительный desktop provider | Смешанные лицензии; основной проект GPL3+. Исключить из минимального audio-профиля |
| [AirConnect](https://github.com/philippe44/AirConnect) | Опциональные UPnP/Chromecast bridges | Не заменяет произвольный PCM→HomePod sender. Отдельный профиль и аудит third-party |
| [airplay-spec](https://github.com/openairplay/airplay-spec) | Читаемые reverse-engineered заметки | Не официальная спецификация Apple; сверять с кодом и опытами |

Текущий общий репозиторий GPL-3.0-or-later. Сборка без видео сама по себе не меняет лицензию. Для заимствований сохранять происхождение, авторство, commit и лицензию каждого файла. Отдельный процесс — техническая граница, а не автоматическое решение любого лицензионного вопроса.

## Контракты, которые стоит закрепить до переноса

1. **Capabilities.** Один реестр формирует Bonjour, `/info`, MRP DeviceInfo и доступность API. Объявлять только собранные и доступные возможности. Runtime-конфигурация может сужать сборку, но не включать отсутствующий код.
2. **HostMediaProvider.** Адаптер отдаёт PCM с форматом и временными метками, метаданные и artwork; получает play/pause/seek/volume и события focus. Голос Алисы не входит в передаваемый контент.
3. **Clock/Timeline.** Для одного источника/relay-сессии — общий media epoch и последовательность кадров локального вывода и всех отправителей; независимые одновременные потоки имеют отдельные timeline. Подключение нового получателя не сбрасывает epoch. Транспортные PTP/NTP соответствия отделены от позиции контента.
4. **GroupCoordinator.** Один источник membership, идентичности и роли лидера. Add/remove/set идемпотентны. Запрос, подключение, подтверждённое воспроизведение и ошибка — отдельные состояния. Галочка на iPhone сама по себе не подтверждает поток.
5. **Volume.** Отдельные user gain, group gain и duck gain. Индивидуальный ползунок меняет конкретного участника. Быстрые изменения объединяются до последнего значения; RTSP-ответы проверяются по CSeq. Сетевой timeout одного HomePod не блокирует локальный звук.
6. **Events/API.** Версия, capability negotiation и явные ошибки. События начала/конца AirPlay дают адаптеру управление подсветкой без знания её реализации в ядре.
7. **Resource bounds.** Ограничить очереди аудио/управления, размер кадров, число соединений, логи и дочерние процессы. В проверенном коде встречаются unbounded control channel и места буферизации без явного лимита; это пункты аудита, не завершённое заключение по безопасности всего проекта.

Сдвиг «−1 с» не должен означать воспроизведение ещё не полученного аудио. Компенсацию строить через общий буфер и presentation timestamps: локальный выход задерживается до согласованного времени получателей. Отрицательное относительное смещение допустимо только в пределах накопленного буфера. Голос Алисы остаётся локальным и своевременным; приглушение контента применяется отдельным gain, не перезаписью пользовательской громкости.

## Профили сборки

Минимальный embedded audio profile: AP1/AP2 RX, audio TX, MRP, timing, нужные кодеки, один platform backend. Без video/mirror/HLS/capture и необязательных desktop-зависимостей. Расширенный desktop profile может включать их.

Это **целевая схема**, не существующие параметры CLI: Cargo features должны разрывать зависимости модулей и регистрацию сетевых handlers. AAC/audio FFmpeg-зависимости нельзя случайно выключить вместе с video: разделить codec features. Проверка минимального профиля должна смотреть дерево зависимостей, размер бинарника и реально объявляемые capabilities.

## Порядок работы и параллельные направления

### 0. Сохранить рабочие результаты и зафиксировать baseline

Перед переносом архивировать не только ветки, но и dirty-файлы Claude. В локальном scratch checkout `feature/homepod-picker` на `e2bd2700be7f22305a8fdd47ce54eeaeb7385228` есть незакоммиченные `src/airplay_sender/src/main.rs` и `src/group_helpers/content_reader.c`. Streaming-reader ABI согласован с вызывающим кодом именно dirty-версией; перенос только commit сломает этот путь.

Сохранить отдельно стабильный main Станции `eaeefb9acfb00a1556d814b6844b12423820402e` и recovery/WIP. Уже имеющееся исправление общей timeline `0df97db7860b510fb456215504bafcdcea672502` учитывать, а не повторять старый диагноз сброса epoch. Реальная акустическая синхронность ещё требует проверки.

### 1. Независимые работы без установки на Станцию

- **MRP:** вынести framing/protobuf/DeviceInfo/player/queue/artwork/commands; отделить callbacks Станции. Сопоставить main и свежую Claude-ветку, не брать старый снимок целиком.
- **Media/TX:** сохранить и протестировать sender, общий timeline и контракт PCM; проверить streaming-reader ABI. Сначала null/file sinks и fake receivers.
- **Capabilities/build/spec:** разделить Cargo features, собрать минимальный audio profile, закрепить source ledger и matrix протокола.

Один интегратор владеет общими API и схемами. Каждый поток пишет в свою область; общие изменения проходят согласование до merge. Проверки исходников и fixtures параллельны; тесты, которые меняют одни физические устройства, выполняются последовательно.

### 2. Собрать общее ядро вне Станции

Поднять MRP server и RX/TX на ПК/стенде. Проверить initial metadata/artwork при подключении посреди трека, команды, churn участников, независимую громкость и уведомления для нескольких наблюдателей. CI: malformed frames, lifecycle/flush, queue limits, cancellation, reconnect, pairing persistence и interop с независимым клиентом.

### 3. Подключить адаптер Станции в тестовом режиме

Сначала сборка и null output без захвата ALSA/микрофона/Bluetooth, без дублирующих активных Bonjour-идентичностей. Дальше один реальный аудиопуть за раз с сохранённым откатом. Старый Shairport сохраняется как baseline до прохождения приёмки нового ядра.

Критерии: Алиса слышит и отвечает; её контент, входящий AirPlay и Bluetooth работают; голос Алисы не ретранслируется; контент приглушается; локальный и удалённый вывод согласованы; add/remove и индивидуальная громкость работают; initial artwork приходит без следующего трека; подсветка остаётся белой на 33% без синего мигания. Для HomePod пользователь установил тестовый уровень 33% — не повышать автоматически.

Отдельно длительный тест RAM/диска/process count: история с заполнением `/tmp` и зависанием штатных служб показывает, что функционального smoke test недостаточно. Не считать доказанным, какой процесс занял последний свободный мегабайт.

### 4. Переключить production только после приёмки

Закрепить релиз ядра, атомарно установить адаптер, сохранить backup и команду rollback. Pairing identity переносить через проверяемую миграцию с резервной копией, не публикуя ключи. Лишь после этого убрать обязательную зависимость от Shairport; оставить возможность возврата на предыдущий релиз.

## Что считать завершением

Не «всё AirPlay реализовано», а конкретный подтверждённый профиль: например audio RX/TX + MRP + groups на перечисленных версиях iOS/HomePodOS и hardware. Таблица протокола обновляется вместе с кодом и свидетельствами. Производительность подтверждается измерениями CPU/RSS/latency/dropouts и синхронности, а не выбором языка Rust.
